How our drive-unit router works, and why we trust it

A plain-language walkthrough of the planner in ar_hackathon/api/routing.py, the scores it gets, and the evidence behind them.

Thirty-second version. The game is deterministic and we are handed the whole floor every step, so instead of reacting we plan. The router carries an exact copy of the game engine, proposes full schedules for every robot, plays each one forward to see the real score it would earn, keeps the best, and hands the engine only the very next move. It repeats that every time step, so new pods are folded in the moment they appear.

01What the engine asks of us

Every time step the engine polls each idle robot, lowest id first, and asks for one adjacent node or a wait. Pickups and drop-offs are automatic when a robot stands on the right node. Aisles and nodes may have capacities, and a full one silently turns our move into a wait. Each delivered pod scores 100 · e−duration/50, so a pod delivered in 10 steps is worth 82 points and one delivered in 50 steps is worth 37. Undelivered pods score zero.

02The planning loop, one step at a time

  1. Snapshot. Copy the floor into compact arrays: where each robot is, what it carries, which pods are waiting and where they are going.
  2. Assign stops. A plan is, for each robot, an ordered list of stops such as “pick up P3, pick up P4, drop at Station 2”, plus the order in which robots get routing priority. Capacity-2 robots batch two pods with the same destination naturally.
  3. Route in time. Each robot's stops become a space-time path found by A*. A reservation table records who occupies each aisle and node at each step, including the engine's rule that the lower id commits first, so a robot waits or takes a detour exactly when the engine would otherwise block it. This is what wins the narrow-bridge case in level 2.
  4. Replay the engine. The candidate schedule is executed inside a line-for-line replica of the engine's step loop, which returns the score the real engine will give for every pod currently on the floor.
  5. Improve, then emit. Local search tries moving a pod to another robot, swapping two pods, reordering a robot's stops, changing priority, and a larger rip-out-and-reinsert move. Only the first move of the best plan is returned; the plan itself is kept as the starting point next step.

Two smaller rules matter a lot. Idle robots park on storage nodes, busiest first, so a newly spawned pod is picked up the step it appears. And a robot never idles on a capacity-limited station dock, which was the single biggest loss in early versions of level 3.

“Knowing the future” is the same planner given every pod's arrival time in advance and three times the compute. It is a reference, not a submission. The per-pod bound treats every pod as if it travelled its shortest path alone, so it ignores shared corridors and single docks; the true optimum sits below it.

On 132 randomly generated cases of the same shape, plus 12 larger stress cases, the planner delivers every pod and averages 79.4 against a per-pod bound of 86.6. The clairvoyant reference averages 79.8 on the same suite, so perfect knowledge of the future is worth about half a point. Where the bound is far away the cause is structural: one narrow corridor or one dock caps throughput, and eight pods cannot all be delivered in eight steps.

04Why we trust it

  • The replica is exact. We froze a clairvoyant plan and executed it blindly. Across 50 cases and 274 pods, every predicted delivery time matched the real engine to the step, and the engine rejected zero of our moves.
  • Time limits hold with margin. Worst observed call is 0.26 s against the 1 s limit, and planning time is capped at 45 s per test case against the 2 minute limit. Budgets are checked between candidate evaluations, which each take well under a millisecond.
  • No state leaks between cases. All 138 benchmark cases run back to back in one process score the same as when run in isolation. The planner resets itself when the clock restarts or the floor changes.
  • Nothing external, nothing new. Standard library only, and the file parses as Python 3.7. Every exception degrades to a validity-checked greedy shortest-path step, so the worst outcome is a slow robot, not a lost case.
  • Hand-checked optimum. On level 3 case 5 (one dock, three robots, four pods) the dock cycle arithmetic gives 83.2 as the best possible score, which is exactly what we get.
  • The search has converged. Three independent attempts to beat the planner on the 138-case suite all failed by more than noise: triple the time budget (79.36 vs 79.38), four different construction orders per step (79.35), and perfect knowledge of every future pod (79.78, the only one ahead, and only through information we cannot have).
  • The plan space holds no more. A reference run that enumerates the entire plan space at every step (every assignment, every stop order, every priority order, up to six known pods) scores 79.21 against the online planner's 79.18 on the same 126 cases: identical on 122 of them, about two points better on two, never worse. Whatever score is left on the table is not in the search.
  • Small instances are solved exactly. When at most four pods are waiting and there are at most three robots, which covers every sample case, the planner enumerates every assignment, every stop order and every priority order before the local search runs, so the emitted plan is the best in the whole plan space for that step. On the sample cases it changes nothing, which is the point: the local search was already finding those plans.
  • Strange inputs don't break it. Ten hand-written adversarial cases (unreachable pods and stations, a robot starting on a dock, two robots sharing a start, a capacity-1 storage node, a one-way loop, float and duplicate edges, every node capacity-limited, zero pods, too little time) run without exceptions or timeouts and deliver every deliverable pod.

05What it does not do

It cannot see pods before they spawn. The clairvoyant reference gains a point or two by parking a robot where a pod is about to appear; online we approximate that by parking on the busiest storage nodes. It also does not prove optimality for multi-robot cases: the search is a local search scored exactly, and on the provided cases it lands within half a point of the same search with perfect information and triple the budget.
